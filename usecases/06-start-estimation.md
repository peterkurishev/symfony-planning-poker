# UC-06. Запуск оценки

Владелец запускает раунд голосования по выбранной задаче с таймером.

## Акторы
- Владелец комнаты (основной)
- Участники (получают уведомление)
- Система (таймер)

## Предусловия
- В комнате есть хотя бы одна задача (UC-04).
- В комнате нет активного раунда.

## Триггер
Владелец нажимает «Начать оценку» у задачи.

## Основной сценарий
1. Владелец выбирает задачу и при необходимости меняет длительность таймера (по умолчанию — значение из настроек комнаты).
2. Система проверяет: задача принадлежит комнате, активного раунда нет, длительность от 10 секунд до 30 минут.
3. Система создаёт раунд со статусом `active`, фиксирует время старта и дедлайн = старт + длительность.
4. Система переводит задачу в статус «оценивается».
5. Система планирует автоматическую остановку раунда на момент дедлайна (UC-08).
6. Система уведомляет всех участников: открыта оценка задачи, показывается обратный отсчёт и карточки шкалы (UC-07).

## Альтернативные сценарии
- **2а. Уже есть активный раунд.** Система отказывает и предлагает сначала остановить текущий раунд.
- **2б. Задача уже оценена.** Система предупреждает, что итоговая оценка будет перезаписана после нового раунда, и запускает повторный раунд после подтверждения.
- **Не владелец.** Участник не видит кнопки запуска; при запросе к API получает 403.
- **Участник подключился в середине раунда.** Система показывает ему текущую задачу, оставшееся время и позволяет проголосовать.

## Постусловия
- В комнате есть один активный раунд с дедлайном.
- Все участники видят задачу и обратный отсчёт.

## Примечания к реализации
- PostgreSQL: `rounds` (id, task_id, started_at, duration_sec, deadline_at, finished_at, status: `active` | `finished`).
- Redis: ключ `room:{id}:active_round` → id раунда и `deadline_at`; хеш `round:{id}:votes` для голосов.
- Планирование остановки: Symfony Messenger, сообщение `FinishRoundMessage` с задержкой = длительность; воркер при получении проверяет, что раунд ещё активен (см. UC-08).
- Realtime-событие `round.started` с `task`, `deadline_at`, `scale`. Клиент считает отсчёт по `deadline_at`, а не по локальному таймеру, чтобы избежать рассинхронизации.
